## Findings

### [HIGH] Grown margins never reach the ui runtime layout — ChartState threads insets ONLY, so a titled plot's brush inversion / point-click desyncs from the rendered scene
**Category:** codebase-claim / orthogonality
**Description:** The load-bearing orthogonality claim is "both layout models carry the grown margins, pinned by the cross-model agreement test" (constraint 3, apt-ac05). But the ui model's *runtime* holder is `ChartState`, not the bare `ChartLayout` the AC exercises. `ChartState` stores an `insets: Insets` field only (chart_state.rs:48) and rebuilds `self.layout = ChartLayout::with_insets(...)` on BOTH `set_dimensions` (chart_state.rs:191, the window-resize path) and `set_insets` (chart_state.rs:203) — and `with_insets` FORCES `Margins::default` (chart_layout.rs:82-92). At assembly the only thread into the ui model is `state.update(cx, |s,_| s.set_insets(insets))` (main.rs:1378), fed from `PlotRender.insets`; `PlotRender` has no margins field and there is no `set_margins` call. So the new `with_margins_and_insets` constructor (apt-ac05) is inert on the ui side: nothing carries grown margins into `ChartState`, and even if set once, `set_dimensions` would reset them to default on the first resize. The rendered scene draws marks against the render-side grown-margin layout while `ChartState.plot_area()` (chart_layout.rs:106, driving `contains` / `local_to_normalised` → brush inversion + point-click) uses default margins. A y-title grows the left margin (~+16px) → every gesture x-coordinate on a titled plot inverts ~16px off. Because derived axis titles are the DEFAULT (apt-ac01), left+bottom margins grow on nearly every column-bound plot — so this hits the motivating crossfilter dashboard, exactly the interactive case, and silently regresses the axi-ac03 "point-click hit tests stay consistent with rendered mark positions" guarantee while every specified test stays green.
**Evidence:** apt-ac05; chart_state.rs:48,191,203; chart_layout.rs:82-92 (with_insets forces default margins), :106-113 (plot_area drives inversion); main.rs:1371-1378 (assembly threads only insets)
**Recommendation:** Add an explicit AC (or extend apt-ac05) requiring: (a) `PlotRender` carries the resolved grown margins; (b) `ChartState` stores them as a field fed via a new `set_margins_and_insets` (mirroring `set_insets` at main.rs:1378); (c) `set_dimensions`/`set_insets` rebuild via `with_margins_and_insets` so a window resize does NOT reset margins — with a resize-preservation test (the axis-inset `insets` preservation via `self.insets` in `set_dimensions` is the template); (d) a brush/click inversion round-trip probe on a titled (grown-margin) fixture, extending axi-ac03, not just the static constructor-agreement test.

### [MEDIUM] ParseWarning::NonStringLabel cannot be emitted by resolve_axis_titles — the cited NonNumericInset precedent warns at PARSE time, not in the resolver
**Category:** codebase-claim
**Description:** apt-ac02 and implementation_notes say a non-string `xLabel`/`yLabel` "degrades to the derived default with a `ParseWarning::NonStringLabel`," and the apt-ac02 verification unit-tests this *inside the resolver* ("resolve_axis_titles unit matrix … number/bool → warn + Derive"), claiming it mirrors `NonNumericInset`. But the real `NonNumericInset` warning is emitted at parse time in `walk_plot` (parse.rs:800-808) by scanning `PLOT_INSET_KEYS`; the cited-as-mirror `resolve_plot_insets` (layout.rs:236-253) is a pure, warning-free reader that silently returns `None` for non-numeric. `resolve_axis_titles` runs at ASSEMBLY (main.rs, beside inset resolution) AFTER parsing, and `ParseOutput.warnings` (parse.rs:316) is finalized during parse — a post-parse resolver cannot push into it. The `AxisTitles` ontology has only x/y/plot fields, no warnings channel. So the AC verification clause pins a warn-test to a pure resolver that literally cannot emit it — an internal contradiction that touches the ontology and the "gpui-free pure reader" design. (implementation_notes' "mirror NonNumericInset → NonStringLabel" already signposts the correct parse-time site, so an alert implementer isn't hard-blocked — but the AC contradicts that guidance.)
**Evidence:** apt-ac02 (spec.yaml:32-33) + implementation_notes (spec.yaml:68); parse.rs:800-808 (emission site); layout.rs:236-253 (pure resolver); ParseOutput.warnings finalized at parse.rs:316
**Recommendation:** Split the AC: `resolve_axis_titles` is a pure resolver returning `Override|Suppress|Derive` (no warning); add `NonStringLabel` emission in `walk_plot` alongside the `NonNumericInset` scan (add `xLabel`/`yLabel`/`title` to a keys check), and re-word apt-ac02's verification to test the warning at the parse layer, not the resolver.

### [MEDIUM] No baselined example exercises the per-plot `title` attribute — the gallery Hugh vetoes plot-title styling on will contain zero plot titles
**Category:** test-gap / scope
**Description:** apt-ac04 adds a per-plot title from `plot.attributes["title"]`, and apt-ac09 makes Hugh's gallery ack the veto point for plot-title styling — "size, colour, plot-title placement (left vs centred)." But NO baselined example declares a plot-level `title`: the PNG sweep operates only on `examples/*.yaml` (scripts/compare-example-pngs.sh:25), and every `title:` there is `meta.title` (the window/workspace title, card 0016 — e.g. framed.yaml:11, crossfilter.yaml:2). The spec's own constraint (line 21) locates the `title`/`xLabel` attrs in the *vendored corpus* (presidential-opinion, airline-travelers), which is a parse-sweep concern (apt-ac10), not PNG-baselined — and the corpus doesn't carry a plot-level title anyway. So the before/after gallery renders derived axis titles everywhere but not a single rendered plot title, leaving the explicit left-vs-centred placement veto with no visual to review. apt-ac04's own verification is a synthetic unit scene probe, not a gallery image, so the feature ships unit-tested but visually unreviewed on the one AC (apt-ac09) whose entire payload is visual.
**Evidence:** apt-ac04 (spec.yaml:38-40); apt-ac09 veto text (spec.yaml:58-61); constraint (spec.yaml:21); examples/framed.yaml:10-11 (meta.title); examples/crossfilter.yaml (no plot title); scripts/compare-example-pngs.sh:25
**Recommendation:** Add a plot-level `title` to at least one baselined example — crossfilter is the natural choice (the motivating case; the gallery would then show both derived axes AND a plot title) — so the plot-title styling veto is backed by a real rendered image before the one-time PNG re-baseline.

### [LOW] Multi-mark plots leave the derived-title source unspecified (surfaced from two lenses)
**Category:** missing-requirement / assumption
**Description:** The spec treats the derive source as a single "ChannelMap already in scope" (constraint line 18, apt-ac01, impl-notes line 69), but the multi-mark scene path holds one `channel_map` PER mark (`entry.channel_map`, scene.rs), not a composed plot-level map, and `draw_multi_mark_scene` draws the axes once outside the per-entry loop (scene.rs:321-328). When marks bind the same axis to different columns, the spec never says which entry names the axis. The precedent the spec claims to mirror — axis-inset — *does* compose across all marks (`resolve_insets_for_marks`, inset.rs), so the titles primitive lacks the equivalent composer. Real corpus shapes latent-touch this (rules.yaml: y bound to `y` by the dot, literal 30 by one ruleY, `level` by another). Impact is low today — crossfilter is single-mark per plot, and `entries[0]` is the established in-code default (`infer_multi_mark_scales` reads `entries[0].layout`/extent at scene.rs:224/263, and rules.yaml's dot is `entries[0]` → deterministically "y"). The verifier refuted the non-determinism worry (`ChannelMap.map` is single-valued per channel; `entries` is an ordered slice — no HashMap-order toss-up). The only genuine latent defect is a plot whose FIRST mark is literal-only, where a naive `entries[0]`-only read would drop a bound sibling's title.
**Evidence:** constraint spec.yaml:18 + apt-ac01 (spec.yaml:26-29); impl-notes:68-69; scene.rs:321-328 (axes drawn once), :224/:263 (entries[0] precedent); examples/rules.yaml:29-38
**Recommendation:** Pin one deterministic selection rule in apt-ac01 (e.g. "first entry whose channel_map binds the positional channel to a column," which subsumes the `entries[0]` default and covers the literal-first case) and add a multi-mark unit fixture (rules.yaml shape) to the apt-ac01 matrix; note multi-mark-with-differing-columns as a recorded deferral if not handled.

### [LOW] apt-ac02: "non-string value → warn + Derive" textually contradicts "explicit null → Suppress" for the null input
**Category:** constraint-conflict
**Description:** apt-ac02's description states two rules that collide on `null`: (a) "an explicit null OR empty string suppresses that axis title," and (b) "a non-string value degrades to the derived default with a `ParseWarning::NonStringLabel`." `null` is a non-string value, so both clauses claim it. The verification matrix resolves it authoritatively ("null/\"\" → Suppress; number/bool → warn + Derive"), and the parenthetical "explicit-null = the Mosaic-exact opt-out" plus first-stated ordering reinforce Suppress — so the failure isn't concretely reachable (warn-on-null code would fail the AC's own matrix). A residual textual imprecision only: "non-string" should read "number or boolean."
**Evidence:** spec.yaml:32 (description) vs spec.yaml:33 (verification matrix)
**Recommendation:** Reword the description's third clause from "a non-string value degrades…" to "a number or boolean value degrades…" (non-string AND non-null), so the null → Suppress carve-out isn't contradicted by the warn+Derive rule.

### [LOW] "A title clips along-axis (never into a neighbour)" is unsupported — title ink is drawn unclipped
**Category:** failure-mode
**Description:** The cross-axis half of the fixed-band margin reasoning is sound (a rotated y-title / horizontal x-title / horizontal plot-title each consume only font-height in their margin regardless of text length — so the fixed `TITLE_SIZE+pad` band sizes the margin correctly in all three orientations). But the along-axis containment claim (spec.yaml:19) is false: there is no clip on title ink. The mark clip is popped BEFORE axes/titles draw (scene.rs push at :171/:308, pop at :174/:318, titles at :177-184/:321-328), `draw_text`/`draw_text_rotated` paint with a bare `Affine::translate`, and `compose_dashboard` appends per-plot scenes with no inter-plot clip (scene.rs:379-386). So a pathologically long title's along-axis extent overflows the plot rect and, in a multi-view dashboard, bleeds into the neighbour. It is only a parenthetical; the fixed-band margin design is implementable regardless, overflow is already a recorded deferral, and realistic column-name/author titles don't bleed in the crossfilter case — hence a wording nit.
**Evidence:** spec.yaml:19; scene.rs:171/174/308/318, :177-184/:321-328, :379-386; apt-ac01/apt-ac04 verify ink PRESENCE at a band, never containment
**Recommendation:** Either add a clip around the title/axis band (with an AC asserting a long x/y-title doesn't paint outside the plot rect in a two-plot compose_dashboard fixture), or drop "never into a neighbour" and replace it with the honest statement that long titles overflow (logged alongside the measured-fit deferral).

### [LOW] No AC pins title / tick-label separation — apt-ac01's "ink at the expected band" probe passes even if the x-title overlaps the tick numbers
**Category:** test-gap
**Description:** The card promises margins grow "to fit each title without overlapping tick labels" (scenario line 30). x tick labels sit at `plot_y_end + TICK_LENGTH(5) + LABEL_SIZE(11)` inside the default 30px bottom margin (axis.rs:206); y tick labels are right-aligned at `plot_x_start - 8` extending left by a data-dependent width (axis.rs:238). The spec never pins the title baseline relative to those labels — placement is left to the implementer — and apt-ac01/apt-ac04 verify only that title ink appears "at the expected band," which a band-presence probe passes whether the title clears the labels or draws on top of them. Mitigated: apt-ac05 verifies the margin GROWS by the band (the space that creates separation), placement is directed in prose ("x centred below the tick labels"), and apt-ac09's manual gallery is an overlap-catching visual review named as Hugh's veto. So non-overlap is verified manually, not unverified — a hardening nit, not a defect.
**Evidence:** card 0019 scenario line 30; axis.rs:202-210, :234-243; apt-ac01 (spec.yaml:29), apt-ac04 (spec.yaml:41); apt-ac05 (spec.yaml:42-45); apt-ac09 (spec.yaml:58-61)
**Recommendation:** Optionally extend apt-ac01 to pin the title numerically against the tick-label band (x-title top edge strictly below the x tick-label descender line; y-title right edge strictly left of the widest y tick label) so the card's no-overlap promise is machine-verified rather than gallery-only.

### [LOW] Cross-model agreement test can agree-by-luck on margin transposition, and pins the two constructors rather than the assembly glue
**Category:** test-gap
**Description:** The two layout models represent margins in incompatible shapes — render `layout.rs` uses `Margins { top, right, bottom, left }` (layout.rs:41-59), ui `chart_layout.rs` uses positional `with_margins(w,h,left,top,right,bottom)` (chart_layout.rs:62-79) — so assembly must translate one `AxisTitles`→grown-margins result into both, a live transposition foot-gun. The verifier refuted the "agree-by-luck" mechanism: the spec grows margins FROM the per-side-distinct Observable defaults (top20/bottom30/left40) by a band, so default+band stays distinct and the agreement test's four per-side checks catch a constructor-internal swap. What survives is narrower: apt-ac05 pins the two CONSTRUCTORS against each other, not the two assembly mirror sites (main.rs render vs `ChartState` ui) that compute grown margins from `AxisTitles` — a ui-side-only assembly transposition wouldn't be PNG-visible and no AC exercises assembly cross-model consistency.
**Evidence:** apt-ac05; layout.rs:41-59; chart_layout.rs:62-79, :254-275 (existing agreement test); layout.rs:53-56 (distinct defaults)
**Recommendation:** Explicitly require the extended agreement unit to feed per-side-distinct grown margins (belt-and-braces), and add an assembly-level assertion that the grown margins computed from one `AxisTitles` feed both the render `Margins` struct and the ui 4-arg constructor to equal per-side values — pin the glue, not just the two constructors. (Overlaps with the HIGH finding's recommendation (b)/(c).)

### [LOW] Interval-channel positional axes (x1/x2, y1/y2 rect family) derive no title — the mechanism reads only Channel::X/Y
**Category:** scope
**Description:** The Derive default reads `channel_map.get(Channel::X/Y)` at the axis-draw site (impl-notes:69, constraint:18), but `Channel::X` and `Channel::X1/X2/Y1/Y2` are distinct enum variants (channel.rs:19-31) and `get()` reads only the exact-key column map (channel.rs:112). rect/rectY/rectX marks bind positional extent via x1/x2/y1/y2 with no plain x/y, so `get(Channel::X)` returns `None` and the axis gets no title — mis-classifying a genuine quantitative axis as the "unbound/augment-only" no-title case. In the corpus, rect-histogram.yaml (x-axis untitled, y=count titled) and rect-cells.yaml (BOTH axes untitled → a byte-identical non-move PNG) become the only unlabelled charts in the re-baseline, and apt-ac09 requires every non-move to be investigated. The mechanism is deterministic and fully specified (nothing blocked), a derived title for an interval axis is genuinely ill-defined (x1=lo, x2=hi — neither names the axis), and `xLabel`/`yLabel` give an explicit escape hatch — so "no derived title" is a defensible default; only the spec is silent on it.
**Evidence:** impl-notes:69 + constraint:18; apt-ac01 (spec.yaml:26-29); channel.rs:19-31, :112; examples/rect-histogram.yaml:23-25; examples/rect-cells.yaml:21-25; apt-ac09 (spec.yaml:58-61)
**Recommendation:** State the interval-axis rule explicitly ("no single positional field → no derived title," or derive from x1 / the shared scale label) and add it to the deferred list; name rect-histogram/rect-cells as expected no-title / non-move cases in apt-ac09 so they don't surface as unexplained non-moves.

## Honest Assessment

The spec is well-grounded and close to ready — its precedent-mirroring (axis-inset, resolve_plot_insets, draw_inline_legend, ChromeSnapshot) is accurate and the design intent is coherent — but it is **not yet implementable as written** because of one HIGH gap. The single biggest risk is that the ui-runtime layout (`ChartState`) threads insets only and force-resets margins to default on every resize, so a spec that satisfies apt-ac05 exactly will ship derived-title plots whose brush inversion and point-click silently desync ~font-height off the rendered marks — and because derived titles are the DEFAULT, this regresses hit-testing on nearly every interactive plot, including the motivating crossfilter dashboard, with all specified tests still green. That must be closed with an explicit `PlotRender.margins` → `ChartState` → `set_margins_and_insets` → resize-preservation → inversion-round-trip chain (the axis-inset round needed exactly this ceremony for `insets`). Two MEDIUM fixes are surgical: correct apt-ac02's warning-emission site to parse-time (the AC currently pins an un-writable test on a pure resolver), and add a plot-level `title` to a baselined example (crossfilter) so apt-ac09's plot-title styling veto has an actual image. The six LOWs are wording/hardening polish. None of this is a tabletop reset — the shape is right; it needs the ui-side margin threading spelled out and two AC corrections. REQUEST_CHANGES.
