# Performance baseline — 2026-07-27

> ## The measured render ceiling, and what the skip notes get wrong
>
> *Annotated by hand 2026-07-29. Nothing below was altered: every number is
> exactly as the harness serialised it. Machine-readable copy in the
> `record_status` block of the JSON beside this file.*
>
> **The measurements in this record stand.** No cell carrying a frame number
> drew more than 100,000 primitives, so none is above the ceiling below. The
> two closest — brush-density and brush-binned-density @ 100000, at exactly
> 100,000 — sit 4.4% under it, measured on a different fixture; those are the
> first to re-verify if the fixture or the renderer moves.
>
> **The ceiling is measured, and it is not the cap.** The renderer stops
> drawing between **104,600 dots (inked)** and **104,800 dots (blank: exit 0,
> frame written, every pixel `rgba(0,0,0,0)` — blank, not thinned)**. It is set
> by vello's **fixed 2^21-element `seg_counts` buffer** and is **not a device
> limit**: no adapter limit moves it. A second, exact ceiling sits an order of
> magnitude above — `bin_data` is 2^18 = 262,144 elements, so the encode
> underflows a `u32` at 262,102 dots in that fixture (262,144 − 42 paths of
> frame, grid and axis rule).
>
> **One wording correction.** The skip notes below say a count "exceeds the
> 100000 the renderer can encode in one scene buffer". Both halves are refuted.
> 100,000 is this harness's **policy cap**, not what the renderer can encode —
> it inks up to 104,600. And "one scene buffer" points at the storage-buffer
> binding size, which this adapter reports as **4 GiB** and which does not bind.
> Those strings are left exactly as the harness emitted them; the harness has
> been corrected so later runs say it right.
>
> **A skip is a guard, not a detector.** The harness predicts a blank frame
> from a primitive count computed *before* rendering; it never asks the renderer
> whether the frame had ink in it. Below the cap, a blank frame would still be
> timed and published as a fast one — which is exactly how `crossfilter-dots @
> 100000` got its numbers in the `2026-07-25` record. Closing that needs vello's
> `failed` bit read back through the shell's paint path.

## Interaction latency and frame time vs row count

`direct` disables the automatic pre-aggregation layer; `cubed` is the shipped configuration. Identical code either side of the toggle — the delta is the layer. `cube` shows what the enabled run's layer did: cubes built / **mark re-queries** served from a cube. The second number is not a step count: the engine counts one hit per mark it serves, so a scenario filtering two subscribing marks records two hits per drag step and a twenty-step suite reads `2/40`. `Drag` is the gesture the timed steps imitate: a **brush** moves both interval endpoints inside a chart and exempts its own plot (crossfilter); a **slider** pins its lower end, advances one handle across fixed stops, and filters every view including the contributor's (intersect) — so a slider step re-queries one more view than a brush step at the same row count. **`Settled zoom → data`** is one pan/zoom extent applied to the aggregating plot and every mark of that plot re-queried — the cost a gesture pays ONCE, when it stops. It is printed for both configurations, because the engine now keys a cube off a navigation extent as well as off a selection clause: an extent IS a structured interval clause, and the axes of one that push beneath the `GROUP BY` become the cube's active dimensions. Where the shape yields a cube, read the cubed figure beside `Step → data, cubed` — the two gestures are then the same kind of query over the same pre-aggregate. Where it does not (a row-level mark, or an axis naming an aggregate output), the two zoom columns should agree.

**`Arrow held` is the figure to quote.** It is exact and deterministic — the summed size of every materialised chunk the compose holds at once, read from the batches themselves — so it is the same on any host and reproduces run to run.

`Compose peak RSS` is the whole process's high-water mark across the first full compose — every mark executed, every Arrow chunk assembled, the scene built — sampled from the OS (ps -o rss (~5ms resolution)). Both configurations' windows are shown because they measure the SAME compose work: the first present precedes any interaction, so no cube exists yet either side of the toggle. Each cell is therefore a SINGLE sample of a whole-process quantity, and the gap between the pair is this measurement's run-to-run noise — across the rows above it reaches 2.6x (brush-density @ 100000 rows). **Do not quote a peak without that spread.** The pre-compose floor is not a monotone baseline either: the OS reclaims pages between windows, so it falls as often as it rises and the growth over it is not the compose's cost. `rss_before_mib`, `rss_peak_mib`, `rss_growth_mib` and `rss_samples` are in the JSON per configuration for anyone who wants them.
