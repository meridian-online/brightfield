## Findings

### [LOW] Pre-existing constraint tension: brightfield-ui depends on brightfield-engine
**Category:** architecture
**Description:** The spec states "brightfield-ui must NOT gain dependencies on brightfield-engine or brightfield-sql (the app crate bridges them)". However, `brightfield-ui/Cargo.toml` already depends on `brightfield-engine` on the main branch (from card 0013). This branch does not introduce or worsen this dependency, but the constraint as written is already violated on main.
**Evidence:** `git show main:crates/brightfield-ui/Cargo.toml` contains `brightfield-engine = { path = "../brightfield-engine" }`.
**Recommendation:** Audit whether `brightfield-ui` actually uses `brightfield-engine` at runtime. If it can be removed, do so in a follow-up. If the dependency is load-bearing (e.g. for type sharing), update the constraint documentation to reflect reality.

### [LOW] RGBA-to-BGRA conversion in paint loop
**Category:** performance
**Description:** `ChartElement::paint()` does a per-pixel RGBA-to-BGRA channel swap on every frame (`bgra_pixels.chunks_exact_mut(4)` with `pixel.swap(0, 2)`). For 640x480 this is ~1.2M byte swaps per frame.
**Evidence:** `crates/brightfield-ui/src/chart_element.rs`, paint() method.
**Recommendation:** Not blocking for v2 (the headless pipeline is the deliverable), but when GPU window display is enabled, consider rendering directly to BGRA or using a SIMD-optimised swap.

### [INFO] Spec discrepancy: "5 mark kinds" vs 4 registered
**Category:** doc
**Description:** The spec's ac-01 description says "4 kinds" but an earlier draft referenced "all five mark kinds" in the verification section. The implementation correctly registers 4 kinds (Dot, Line, BarX, BarY). The progress.md notes this: "MarkKind::Bar doesn't exist: spec said 'Bar, BarX, BarY' but enum only has BarX and BarY".
**Evidence:** `default_lowerers()` in `crates/brightfield-sql/src/lower.rs` registers 4 entries. Spec ac-01 description says "4 kinds". Spec ac-01 verification says "all five mark kinds".
**Recommendation:** Clean up the verification text to say "all four registered mark kinds" for consistency. Not blocking.

### [INFO] GPUI window deferred — documented, not a gap
**Category:** doc
**Description:** AC-04 explicitly documents that GPUI window display is deferred (requires Xcode + Metal compiler for `gpui_macos`). The commented-out window code in `main.rs` is well-documented and the headless pipeline is fully functional.
**Evidence:** `crates/brightfield-app/src/main.rs` lines 161-176 (commented GPUI block).

Test coverage is thorough -- every code-type AC has at least one dedicated test, and AC-01 has seven tests covering the lowerer from multiple angles. The existing test suite shows zero regressions. The GPUI window deferral is well-documented and the headless pipeline proves end-to-end correctness. No blocking issues found.
