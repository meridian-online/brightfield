# The pull-request gate

A pull request's checks run on the Mac Studio, not on GitHub's runners. `cargo xtask gate <pr>` runs the full gate there and posts the verdict on the pull request as the `local-gate` commit status. `main`'s backstop is a nightly full gate on the Mac Studio, `cargo xtask nightly`, which posts the `nightly-gate` commit status on `main`'s head. No push, pull request or schedule starts a GitHub-hosted macOS job: hosted macOS runners are for release tags, and for the hosted workflows a person starts by hand.

## Why

Brightfield is the only desktop app in the estate, so it has the heaviest build, and its pull-request checks spent most of their time waiting for GitHub's macOS runners rather than running. From 2026-10-17 to 2026-11-16 the `test` workflow ran 148 times. A median run took 63 minutes end to end against a 37-minute critical path; the rest was queueing for the five macOS runners GitHub's free plan allows across the organisation (job wait p90 29 minutes, max 93). 49 runs were cancelled by a newer push, and 8 of 9 reruns went green. The same steps on the Mac Studio took about 38 minutes with no queue, run one after another.

Brightfield is in early access, and anything that shortens the time from a pushed commit to a merge comes first.

The same queue held up `main`. On 2026-11-18 the hosted `test` run for a merge to `main` waited 75 minutes for a macOS runner, and another repo's distribution run on `main` sat queued behind it, since GitHub's free plan runs at most five macOS jobs at once across the whole organisation. With pull requests already gated on the Mac Studio, the hosted runs on `main` were only a backstop, and the backstop was now what held the queue.

## Rulings

Hugh made these, with the reasons given:

- **The pull-request gate runs locally, not on a self-hosted runner** (2026-11-16). CI was slow and unreliable across the board, and the queue for macOS runners was most of it. A self-hosted runner was set aside because it would run on any push to a public repo, a fork's included; `test.yml`'s disk-reclaim steps delete Xcode versions and simulator runtimes, which suits a throwaway VM and not a workstation; and its jobs would compete with sessions for cores outside the machine's build-slot rule. A Linux VM was set aside too: macOS gives a Linux guest no Metal GPU, so the pixel tier would draw through a software rasteriser on a window stack this repo has never validated.
- **Which workflows leave pull requests** (2026-11-16). `test` (warm-cache and its shards) and `lint` (fmt, clippy, check-release, doc, comment-citations) leave pull requests and run on each merge to `main`, nightly and on demand. `brew-install-branch` and `signing-rehearsal` stay on pull requests, filtered to the packaging paths. `license` and `public-hygiene` stay: they run on Linux in under a minute. `nightly-network` and `release` are unchanged. No workflow was deleted; each runs the same steps it ran before, and only the triggers changed. The 2026-11-18 rulings below moved the hosted runs on `main` and the packaging checks again.
- **The Mac Studio is the reference machine for pixel baselines** (2026-11-17). Keeping hosted tests on the pull requests that touch baselines would have put a quarter of merges (10 of 40 in the month measured) back in the queue.
- **A red hosted run on `main` is flagged and fixed forward, with no revert** (2026-11-17).
- **The gate is a brightfield `cargo xtask` command**, not a script shared across repos (2026-11-17). Only brightfield needs it, and xtask already owns the step list the gate runs.

- **Remove the hosted macOS runners** (2026-11-18). Hugh's words were "let's try to remove any macos runners". The reason is the queue above: GitHub's free plan runs at most five macOS jobs at once across the organisation, and on 2026-11-18 `main`'s test run for a merge queued 75 minutes.
- **The hosted test and lint runs on `main` become a nightly full gate on the Mac Studio** (2026-11-18). It is reported the way the backstop was: a red `main` is flagged on the `main-red` Kata issue and fixed forward, and the pull-request gate's read of the backstop reads the nightly in place of the hosted runs.
- **Checks that need no Mac may run on Linux** (2026-11-18). The rest leave hosted CI.
- **The release workflow and its clean-Mac install check keep GitHub's Macs, for release tags only** (2026-11-18). `release.yml` and `brew-install.yml` are unchanged.
- **The nightly keeps its own clones of Brightfield and open-analytics on the internal disk** (2026-11-18). A launchd job cannot read an external volume without a disk-access grant, and Hugh chose clones over granting `/bin/bash` Full Disk Access.

Other repos keep their pull-request CI: their Linux runners barely queue.

### Decisions taken with the nightly

The agent that planned the nightly made these calls, and Hugh approved them with the plan on 2026-11-18.

- **The packaging checks are run by hand only.** `brew-install-branch` installs the app through Homebrew and `signing-rehearsal` puts a keychain on the user's search list, so on the Mac Studio both would touch Hugh's real Homebrew and keychain, and his ruling keeps the clean-Mac install check on GitHub's Macs. Both lose their pull-request triggers. A pull request touching their paths is checked by them only when a session dispatches the workflow, or at the next release tag; `cargo xtask gate` prints the `gh workflow run` command when a pull request touches those paths (`BREW_INSTALL_BRANCH_PATHS` and `SIGNING_REHEARSAL_PATHS` in `xtask/src/gate.rs`). It does the same for `managed-duckdb.yml` when a pull request touches the managed edition's DuckDB build, its parity check, `Cargo.lock` (which pins arcform) or the release command line's pin (`MANAGED_DUCKDB_PATHS`), since that build and its parity check otherwise run only at night. Keeping their path-filtered pull-request triggers would have been a few macOS jobs a month, and would have brought hosted Macs back.
- **`managed-duckdb` moves from pull requests touching the DuckDB build to the nightly.** A broken DuckDB build is found the night after the merge and fixed forward, not found before it. The Mac Studio has `cmake` and `ninja`, and the build is reused between nights while its inputs are unchanged.
- **The network tests have their own status and issue.** A red `nightly-network` says the published data moved or a host was down far more often than that a commit broke something, so it does not make `main` red. It posts its own `nightly-network` status and comments on, or opens, the Kata issue labelled `nightly-network`, flagged for Hugh; a pass closes it. It had its own workflow before, which the gate never read.
- **A nightly that errors or goes missing says so.** A nightly that stops before its steps posts no status, so the commit keeps its last real verdict, and raises the `nightly-missing` issue itself: a nightly that errors every night is as blind as one that never runs. The pull-request gate raises the same issue when `main` has no nightly verdict newer than 36 hours, and never closes it; only a nightly verdict does. A nightly that cannot even start (the agent unloaded, the machine off) is caught only by the next pull-request gate. No second watcher was built, for the reason given under "Not built".
- **02:30 start, a lock wait to 05:30, 36 hours, and 6 jobs and 6 threads.** The nightly starts at 02:30 local time and waits for the gate lock until 05:30 at the latest, so a full run can still end before the working day. It runs with the caps a Claude Code session has, 6 cargo jobs and 6 test threads, since a LaunchAgent inherits none. A verdict more than 36 hours old counts as missing, which gives a night's slack. The gate lock does not stop a session building Rust overnight from making a fourth build; the three-slot rule stays a convention.
- **The verdict is a commit status, not a local file.** A file would be readable only on the Mac Studio. A `nightly-gate` status is public and durable, shows in Forge and on GitHub beside the commit, and is read from any machine with `gh`. A workflow run could not carry it, since no hosted run does this job now.
- **Only `fmt` and `comment-citations` run on Linux.** `clippy`, `check-release` and `doc` build the whole dependency graph, which on Linux needs the Vulkan, wayland/X11, xkbcommon and fontconfig system packages that this repo has never validated. Making them pass on Linux is separate work for whoever validates Linux. They stay on the nightly and the gate.
- **The Linux lint job runs on pull requests as well as `main`.** It takes about a minute, Linux runners barely queue, and it tells a pull request about a formatting slip before the gate does.
- **The nightly keeps going past a failed step.** `cargo xtask ci --nightly` carries on after a failure, so a clippy slip on `main` does not hide that night's test results, as the separate hosted `lint` and `test` runs never did. A step whose earlier step failed (the two test steps after `warm-cache`) is still skipped. The pull-request gate does not use the flag and stops at the first failure.

### What was set aside

- **A self-hosted runner for the nightly.** The 2026-11-16 reasons above still hold for a public repo, and nothing here reopens them.
- **A local file for the verdict.** See the commit-status decision above.
- **Deleting the hosted macOS workflows.** As on 2026-11-16, each keeps its steps and loses only its automatic triggers, so `gh workflow run <file> --ref <branch>` still runs it.
- **Running `brew-install-branch` and `signing-rehearsal` on the Mac Studio.** See the packaging decision above.
- **Removing the hosted-runner pixel jitter allowance** in `gpu_jitter.rs`. A hosted run started by hand still draws on that runner.

## What `cargo xtask gate <pr>` does

1. **Takes the gate lock.** One gate runs on the machine at a time: an OS advisory lock on `~/.cache/meridian/gate/gate.lock`, so a crashed gate never blocks the next. A waiting gate says who holds the lock and polls every 30 seconds. While a session's gate runs, that is the session's one cargo build.
2. **Reads `main`'s backstop.** It reads the newest commit among `main`'s last 50 that carries a `nightly-gate` status of `success` or `failure`, in one GraphQL call through `gh api graphql`. On a `failure` it opens the one Kata issue labelled `main-red` (or finds the open one), flags it for Hugh, and comments the commit once. On a `success` it says so on that issue and closes it. When the verdict is more than 36 hours old, or there is none, the nightly is missing: the gate says so and raises the `nightly-missing` issue, with a comment at most once a day, and never closes it. A red or missing nightly does not stop the pull request's gate, since the fix goes forward. Each call it makes to GitHub or Kata times out after 120 seconds, so a hung call cannot hold the lock.
3. **Builds the tree to test.** It refuses a pull request whose head is not in `meridian-online/brightfield`: the gate runs the branch's code on the Mac Studio, and the isolated environment below is test hygiene, not containment. It fetches the head and `origin/main` and makes a clean worktree at the head merged with `main`, as GitHub's pull-request checks test it. The worktree goes under `~/.cache/meridian/gate/trees/`, beside the gate's target directory, as a checkout's tree sits beside its own `target` in CI: a test that spells a scratch file relative to its working directory then climbs a few levels, not to `/`. A merge conflict fails the gate with "merge main into the branch first".
4. **Isolates the environment.** Every step runs with `HOME` and `TMPDIR` pointing at fresh temporary directories, the real `CARGO_HOME` and `RUSTUP_HOME`, a persistent target directory under `~/.cache/meridian/gate/` so a run reuses compiled dependencies (the workspace's own crates rebuild, since each run's worktree is new), the DuckDB CLI the merged tree pins (the invoking checkout's copy when the tree's `fetch-duckdb-cli.sh --check` accepts it, else one the tree's script fetched into `~/.cache/meridian/gate/duckdb-cli`, so a branch that moves the pin still gates), and the real `open-analytics` checkout. The machine's cargo job cap stays in the environment, since it changes no build output; compiler and build-flag variables are removed, so the build is CI's.
5. **Runs the steps.** It posts a `pending` status, then runs the merged tree's own `cargo xtask ci`, so the steps are the pull request's and not those compiled into the checkout that started the gate. The output is teed to `~/.cache/meridian/gate/logs/pr-<pr>-<sha>.log`, and the gate prints its path. When the pull request changes a file the packaging checks read, the gate first prints the `gh workflow run` command for the matching hosted check, since those checks no longer run on pull requests.
6. **Posts the verdict.** A `local-gate` status, `success` or `failure`, on the head commit, with a description under GitHub's 140 characters naming the steps passed, the failing step if any, the wall time and `main`'s short SHA, for example `failed at test-default after 33 steps, 37m 01s, on main 09c2efb`. A run that leaves no step summary is a failure, never a pass, so an empty run cannot pass for a full one. Every failure after the head is known is posted.
7. **Cleans up** the worktree and temporary directories and releases the lock.

Start a gate from a checkout that already reads the nightly's `nightly-gate` status: merge or rebase `main` into the branch first, since a gate started from an older checkout still reads `main`'s retired hosted `test.yml` and `lint.yml` runs for its backstop.

The status attaches to the head commit, as GitHub's checks do. A later push leaves the old status on the old commit, and Forge shows the new head as unchecked until the gate runs again. A move of `main` after the gate ran does not invalidate the status, which matches how GitHub's own checks behave. `local-gate` is not a required status in a GitHub ruleset: only Hugh merges, he sees the status in Forge, and a required status would make every pull request, docs-only ones included, wait for a gate run.

## The two test steps run side by side

A full `cargo xtask ci` runs `warm-cache` as a local step, which builds every test binary once, and then runs `test-one-thread` and `test-default` at the same time against the built binaries, so neither waits on cargo's build lock. Inside a Claude Code session, whose settings set `RUST_TEST_THREADS` to 6, the pair uses about seven threads, one over a session's cap; from a plain terminal `test-default` uses every core. `test-default`'s output goes to `target/xtask/test-default.log` while the pair runs, and its failure excerpt is printed in the summary.

Running them together surfaced two tests that shared files across processes: five shell test targets pointed brightfield's config directory at one `CARGO_TARGET_TMPDIR/config`, which every test target of the crate shares, and one target removed a data file there that another target, in the other group, could be opening. Each target now uses a config folder named after it. A test that writes outside a folder of its own will race under the gate.

The first passing gate run, in November 2026 with two other sessions building Rust on the machine, took 1 hour 4 minutes: 2 minutes 21 seconds for `warm-cache`, then 16 minutes 17 seconds for `test-one-thread` and 57 minutes 18 seconds for `test-default`, overlapping.

## Pixel baselines

The reference machine is the Mac Studio's Apple M5 Max. Every committed baseline is drawn on it, and on it every snapshot is held to `kittest.toml`'s floor with no pixel past the threshold. When the reference moved there, 22 of 191 images changed, all by rasteriser rounding: at most 14 of 255 in any channel and 23 pixels in any image.

The hosted macOS runner's paravirtual GPU rounds a few pixels of some baselines differently. `crates/brightfield-shell/tests/support/gpu_jitter.rs` allows each test the failed-pixel count a hosted run measured for it, on that runner's adapter alone; every other GPU keeps zero. Each binary that takes a budget writes the adapter's name to stderr, so a hosted log says which GPU a run drew on. A test that calls `image_snapshot` directly takes the floor everywhere until a hosted run measures jitter on it.

A redrawn image counts as rounding when no pixel moves more than 16 of 255 in any channel and at most 50 pixels move. An image past either limit keeps its old baseline and is raised with Hugh, and so is a test that would need more than 50 failed pixels on the hosted runner. A baseline is never drawn from a hosted run's output.

## The nightly

`cargo xtask nightly --sha <sha>` runs the full gate on `main`'s head and posts the verdict. A LaunchAgent starts it at 02:30 local time every day (launchd also fires a missed start when the machine wakes). A nightly whose commit already has a `nightly-gate` `success` still runs, since the network tests and the steps that read advisories can go red with no new commit.

**The launcher.** `scripts/nightly/install.sh install` renders `scripts/nightly/online.meridian.brightfield-nightly.plist.in` with the user's home, writes it to `~/Library/LaunchAgents/`, copies `scripts/nightly/run.sh` to `~/.cache/meridian/gate/nightly/run.sh`, and loads the agent. The agent runs that copy and not the checkout's file, which is whatever branch the checkout is on. The copy fetches `origin/main` into the nightly's own clone of Brightfield, which serves only as an object store, makes a fresh detached worktree at that commit under `~/.cache/meridian/gate/trees/`, runs that tree's own `scripts/nightly/run.sh`, and removes the worktree whatever the outcome, so every line of code the nightly runs is `main`'s. Each run makes its own worktree, so a run started by hand beside the scheduled one cannot remove the other's. A `nightly-*` tree more than a day old, left by a run that was killed, is removed at the start of the next. The installed copy replaces itself with `main`'s `run.sh` when that differs, so a change to the launcher reaches the next night without a reinstall; a trial never replaces it. `install.sh uninstall` removes the agent and the copy and leaves the logs, and `install.sh status` shows whether the agent is installed and loaded. A main run that stops before `cargo xtask nightly` starts (the fetch fails, the worktree cannot be made, the tree's toolchain is not installed, or xtask does not build) raises `nightly-missing` from the launcher, with the same title and attention line xtask uses and a comment, once a day, naming the step it stopped at; a trial raises nothing.

**The nightly's own clones.** The nightly keeps its own clones of both repositories under `~/.cache/meridian/gate/nightly/`, `brightfield/` and `open-analytics/`, and fetches both each night; the first run makes whichever is missing, so `install` needs no checkout beyond the scripts. A launchd job cannot read an external volume without a disk-access grant, the checkouts live on one, and Hugh chose clones over granting `/bin/bash` Full Disk Access on 2026-11-18. Both clones are object stores only: each run makes its own detached worktree of open-analytics' fetched `main` under `~/.cache/meridian/gate/trees/` and passes it to the gate as `OPEN_ANALYTICS_DIR`, so the nightly tests open-analytics' `main`, whatever a developer has checked out beside Brightfield, and a run started beside another cannot rewrite the tree the other is reading. The run removes that worktree with its Brightfield one. A clone or fetch that fails raises `nightly-missing` like any other stop before xtask, with a step naming the repository. `BRIGHTFIELD_NIGHTLY_REPO` may name another Brightfield repository in place of the clone.

**To run it now:** `scripts/nightly/install.sh run-now` runs the nightly in the foreground against `main` through the same clones launchd uses, with the 6-job and 6-thread caps. `BRIGHTFIELD_NIGHTLY_REF=<ref>` names another ref, which runs as a trial: it posts both statuses but raises and clears no issue, since its commit is not `main`'s. Its output goes to the terminal as well as the log. The agent's own output goes to `~/Library/Logs/brightfield-nightly/`.

**What a run does.**

1. **Takes the gate lock**, as a pull-request gate does, so the nightly never runs beside a gate and counts as one build slot. A run started before 05:30 waits for the lock until 05:30 at the latest; a run started by hand between 05:30 and noon does not wait; a run started after noon waits until the next 05:30. A nightly that never gets the lock posts no status.
2. **Checks the tree and isolates the environment** as the gate does: it refuses a tree whose head is not the commit it was asked to gate or that has uncommitted changes, then runs with a fresh `HOME` and `TMPDIR`, the real cargo and rustup homes, the gate's target directory, the pinned DuckDB CLI, the real `open-analytics` checkout, and compiler and build-flag variables removed. A missing `open-analytics` checkout or DuckDB CLI stops the run before the steps, naming which.
3. **Posts nothing yet.** GitHub keeps only the latest status per context on a commit, so a `pending` posted at the start, or an `error` after an early stop, would overwrite an earlier night's verdict on the same unchanged head.
4. **Runs `cargo xtask ci --nightly --summary-json`** in the tree. It runs every step of the gate, carrying on past a failed step, then the nightly-only steps, each whether or not the gate passed, so one bad night reports everything that is red. The output is teed to `~/.cache/meridian/gate/logs/nightly-<sha7>-<YYYYMMDD>.log`.
5. **Posts the verdict** on the commit and keeps the issues in step, as the next section says.

The nightly-only steps, which `cargo xtask ci --list` marks and `--step <name>` runs by hand, and a pull-request gate does not run:

- `nightly-network`: the network-gated `--ignored` tests and the real FineType bundle checks, in `scripts/nightly-network.sh`. `nightly-network.yml`, run by hand, calls the same script.
- `duckdb-managed`, then `managed-duckdb-test`, then `duckdb-parity`, with `BRIGHTFIELD_DUCKDB_MANAGED_DIR` under `~/.cache/meridian/gate/duckdb-managed`. A cold DuckDB build takes 30 to 90 minutes, so the build is kept between nights and rebuilt only when the hash of its inputs changes, the files `managed-duckdb.yml` keys its cache on. `duckdb-parity` holds that build to DuckDB's release command line (`docs/managed-duckdb.md`, "What checks it"), with `BRIGHTFIELD_PARITY_DIR` under `~/.cache/meridian/gate/duckdb-parity`, so its two builds of arc, one of them compiling DuckDB, are kept between nights too.

### Statuses and issues

| Outcome | Status on the commit | Issue |
| --- | --- | --- |
| Every step but `nightly-network` passed | `nightly-gate` `success` | `main-red` closed with the commit as evidence |
| A step failed, or the run left no summary | `nightly-gate` `failure`, naming the first failed step, for example `failed at test-default and 1 more after 33 steps, 52m 10s` | `main-red` opened or found, flagged for Hugh, with a comment naming the commit, the failing step and the log's path, once per commit |
| `nightly-network` passed | `nightly-network` `success` | `nightly-network` issue closed |
| `nightly-network` failed | `nightly-network` `failure`; `nightly-gate` is unaffected | `nightly-network` issue opened or commented on, flagged for Hugh |
| The run stopped before its steps (lock still held at 05:30, `open-analytics` or the DuckDB CLI missing, the run could not start, the tree did not match, or the launcher stopped before xtask started) | none, so the commit keeps its last real verdict | `nightly-missing` opened or commented on, flagged for Hugh |

A `nightly-gate` status that could not be posted raises `nightly-missing` too, and no issue follows a status that was not posted, so no issue says what a reader of the commit cannot see. The next `nightly-gate` verdict, success or failure, closes `nightly-missing`. The nightly posts two status contexts, `nightly-gate` and `nightly-network`, and keeps three issue labels: `main-red`, `nightly-network` and `nightly-missing`. The exit code is 0 only when both statuses were posted and both are `success`.

## The workflows

`test.yml`, `lint-macos.yml`, `nightly-network.yml`, `managed-duckdb.yml`, `brew-install-branch.yml` and `signing-rehearsal.yml` run by hand only (`gh workflow run <file> --ref <branch>`), and a hosted run answers only what GitHub's runner alone can, such as whether a clean macOS image still builds. Each file's header says which nightly step or release check covers it. `lint.yml` is a Linux workflow: it runs `fmt`, `comment-citations` and the comment-citations self-test on each pull request, each push to `main` and by hand. `license` and `public-hygiene` are Linux and unchanged. `release.yml` and `brew-install.yml` run on a release tag on GitHub's Macs, unchanged. `lint-macos.yml` is a file of its own because a workflow's triggers cover all its jobs, and `workflow-coverage` reads them per workflow.

`workflow-coverage` reads the workflow files. Every step `cargo xtask ci` carries must be invoked by some workflow, a by-hand one counting, so a hosted run of any step stays possible; no workflow may invoke a step the command lacks; and a workflow that starts on its own may not call a gate script or cargo directly. A job whose `runs-on` names a macOS image may sit only in a workflow whose triggers are `workflow_dispatch`, `workflow_call`, or a push of tags alone, and a workflow with any other trigger may not call a workflow that has a macOS job. A hosted macOS job therefore cannot return on a push, a pull request or a schedule without the check failing.

## Not built

- A background poller for red runs on `main` (a launchd job). It would notice sooner, but it is one more process on the Mac Studio that nobody watches. This was set aside while hosted CI was the backstop; the nightly is a scheduled job, but it is the backstop itself rather than a watcher beside one, and the missing-nightly check answers the objection that nobody watches it: a nightly that errors raises `nightly-missing` itself, and a pull-request gate raises it after 36 hours without a verdict. A nightly that cannot start at all is caught only by the next gate, since a second watcher would be the unwatched process again.
- A count of build slots. The three-session rule is a convention, and the gate lock is the only counter.
- Making `clippy`, `check-release` and `doc` pass on Linux, which needs the window stack's system packages validated there.
