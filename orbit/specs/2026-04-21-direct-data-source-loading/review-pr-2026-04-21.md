## Findings

### [MEDIUM] F1: AC-06 warning for unknown CSV extras not implemented
**Category:** test-gap
**Description:** Spec constraint 4 requires: "Extras outside allow-list -> `ParseWarning::UnknownOption` (reuse card 0001's warning type)." AC-06 verification specifies a test named `dfsql_csv_unknown_extra_warns` asserting that extra `encoding: utf8` produces a warning, not an error. The implementation instead names the test `dfsql_csv_unknown_extra_ignored` and only verifies the extra does not appear in SQL output — it does not produce any warning. The `emit_sources` signature `Result<Vec<SourceDdl>, EmitError>` has no channel for returning warnings alongside successful results.
**Evidence:** `crates/brightfield-sql/tests/emit_tests.rs:118` — test named `dfsql_csv_unknown_extra_ignored`, not `dfsql_csv_unknown_extra_warns`. Grep for `UnknownOption` in `crates/brightfield-sql/` returns zero matches. The function signature in `crates/brightfield-sql/src/emit.rs:80` returns `Result<Vec<SourceDdl>, EmitError>` with no warnings vector.
**Recommendation:** Either (a) extend the return type to include a warnings channel (e.g. `(Vec<SourceDdl>, Vec<ParseWarning>)` inside the Ok), or (b) accept this as a deliberate deferral and document it as a detour in progress.md — then rename the test to match the spec's expected name and add a TODO comment. Option (b) is lighter and aligns with the "pure emission" constraint; warnings can be produced at a higher layer that has access to the allow-list.

### [LOW] F2: Deviation ID DEV-0002 vs spec constraint DEV-0001
**Category:** deviation
**Description:** Spec constraint 6 says the DuckDB ATTACH divergence is "recorded in `deviations.yaml` as `DEV-0001`". The implementation uses DEV-0002 because DEV-0001 was already taken by a pre-existing rendering deviation. This is correctly documented in `progress.md` as a detour, and the implementation is internally consistent — deviations.yaml, DEVIATIONS.md, and the conformance layer all reference DEV-0002 correctly.
**Evidence:** Spec constraint 6: "recorded in `deviations.yaml` as `DEV-0001`". `deviations.yaml` diff: `id: DEV-0002`. `progress.md` detour log: "DEV-0001 already taken by rendering deviation — used DEV-0002".
**Recommendation:** No code change needed. This is a spec-reality divergence that was correctly navigated at implementation time. The spec constraint is now stale on the ID number only — the intent (register the deviation) is satisfied.

### [LOW] F3: DEV-0001 suppression scope narrowed without spec authority
**Category:** scope
**Description:** The implementation removes layer 2 from DEV-0001's `conformance_layers_suppressed` list (was `[2, 3, 4]`, now `[3, 4]`). This is correct behaviour — layer 2 is now active and DEV-0001's rendering divergence doesn't affect DDL emission — but neither the spec nor any AC mentions modifying DEV-0001.
**Evidence:** `deviations.yaml` diff: `conformance_layers_suppressed: [2, 3, 4]` changed to `[3, 4]`. Spec mentions DEV-0001 zero times (only constraint 6 mentions a deviation, and it references the wrong ID).
**Recommendation:** No change required. The modification is logically necessary — layer 2 cannot both be active for conformance and suppressed by a deviation. The progress.md detour log covers this. Noting for traceability only.

## Honest Assessment

This is a solid, well-structured implementation that closely follows its spec across 17 acceptance criteria. The new `brightfield-sql` crate is cleanly designed — pure function emission, no I/O, deterministic canonicalisation, comprehensive per-format dispatch with error paths. All 107 workspace tests pass. The conformance layer correctly flips from Pending to active for all 10 curated corpus specs. The deviation registry is properly maintained.

The one substantive gap is F1: the spec explicitly requires unknown CSV extras to produce `ParseWarning::UnknownOption`, but the implementation silently drops them. The `emit_sources` return type has no warning channel. This is not a correctness bug — the emitted SQL is correct regardless — but it violates a spec constraint and the AC-06 verification. The fix could be as simple as documenting this as a deferral (the warning can be produced at a higher call site that already has access to parse warnings) or extending the return type to carry warnings. Either way, the test should be renamed to match the spec.

The DEV-0001/DEV-0002 ID mismatch and suppression scope change are well-documented implementation-time decisions that don't need code changes, just traceability awareness.
