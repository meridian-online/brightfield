## Findings

### [CRITICAL] ac-02 test does not verify subscriber dispatch — no marks actually subscribe

**Category:** test-gap
**Description:** AC-02 requires: "load a spec with a param and two subscribing dot marks with data.from. Call propagate_param with a new value. Assert both marks return Ok with RecordBatches." Neither `rpw2_ac02` test creates a spec where marks are actually in the subscriber graph for the param. The marks use `data: { from: t }` but never reference `$brush` or `$threshold` in any expression, so the subscriber graph has zero mark entries for those params. Both tests only assert `param_state` was updated — they never assert that `results` contains Ok entries with RecordBatches. The test `rpw2_ac02_propagate_param_dispatches_to_subscribers` even acknowledges this in its comment: "Since the mark doesn't reference $brush, results should be empty."

**Evidence:** `crates/brightfield-engine/src/lib.rs` — both rpw2_ac02 tests. The `_results` variable is prefixed with `_` (unused) in the first test. The second test discards results entirely.

**Recommendation:** Create a spec where a mark references the param (e.g., via `filterBy: "$threshold > 10"` or an expression channel). Assert that `results.len() > 0` and that the results contain `Ok` entries with non-empty RecordBatches. This is the core contract of `propagate_param` — dispatching to subscribers — and it is untested.

### [CRITICAL] ac-04 test does not exercise partial failure

**Category:** test-gap
**Description:** AC-04 requires: "load a spec with two marks subscribing to the same param — one valid (dot) and one invalid (rect, unsupported lowerer). Call propagate_param. Assert one Ok result and one Err result." The actual test (`rpw2_ac04_partial_failure_one_ok_one_err`) uses a spec with a single dot mark that does not reference `$val`, so the subscriber graph has zero subscribers. The test only checks that `param_state` was updated. It never asserts the presence of both Ok and Err results. The test comment even acknowledges: "Results may be empty (no subscribers reference $val in this spec)."

**Evidence:** `crates/brightfield-engine/src/lib.rs:1153-1190` — the test body. `let _ = results;` discards the results entirely.

**Recommendation:** Create a spec where the param appears in two marks' expressions — one dot (supported) and one rect (unsupported lowerer). Both marks must reference the param so they appear in the subscriber graph. Assert `results.len() == 2`, with one Ok and one Err. Without this, the partial-failure path in `propagate_param` (the `continue` on emit error) is dead code from a test coverage perspective.

### [LOW] execute_all does not directly pass param_state — relies on delegation chain

**Category:** assumption
**Description:** AC-06 requires `execute_all` to use `param_state` when emitting queries. The implementation achieves this indirectly: `execute_all` calls `execute_mark`, which now passes `&self.param_state` to `emit_query`. This is correct and sufficient. However, the `rpw2_ac06` test only verifies `current_params()` state management — it does not assert that a query emitted after `propagate_param` actually contains the param value in its SQL. This is acceptable given that `emit_query`'s param injection is tested in brightfield-sql, but noted for completeness.

**Evidence:** `execute_all` at line 181-184 delegates to `execute_mark`. `execute_mark` passes `Some(&self.param_state)` when non-empty.

**Recommendation:** No action required. The delegation chain is sound. A future integration test that inspects emitted SQL would strengthen confidence but is not blocking.

### [LOW] execute_mark passes None when param_state is empty — subtle semantic difference from always passing state

**Category:** edge-case
**Description:** `execute_mark` conditionally passes `None` vs `Some(&self.param_state)` based on `self.param_state.is_empty()`. This means a spec with zero params behaves identically to pre-change code (emit_query gets None). This is safe and preserves backward compatibility. However, if a param is added dynamically via `propagate_param` and then removed (not currently possible), the empty-state check would revert to None semantics. This is a non-issue today but worth noting.

**Evidence:** `crates/brightfield-engine/src/lib.rs` — `execute_mark` method, the `if self.param_state.is_empty()` guard.

**Recommendation:** No action required. The current approach is correct for all current use cases.

## Honest Assessment

The implementation is clean, well-structured, and correctly adds the `param_state` field, `current_params()` accessor, and `propagate_param()` coordinator method. The code handles all edge cases specified: unknown params, unsubscribed params, Selection param exclusion, and the partial-failure `continue` pattern. All 320 existing tests pass with zero regressions. However, the two critical ACs — ac-02 (subscriber dispatch) and ac-04 (partial failure) — have tests that do not actually exercise the paths they claim to cover. None of the rpw2_ tests create a spec where a mark is in the subscriber graph for a param, meaning `propagate_param`'s core dispatch loop (steps 3-4 in the method) has zero test coverage for the happy path. The state management plumbing is well-tested, but the subscriber-driven re-execution — the spec's stated goal — is not. Adding two tests with specs that wire marks into the subscriber graph would close this gap and bring the PR to APPROVE.
