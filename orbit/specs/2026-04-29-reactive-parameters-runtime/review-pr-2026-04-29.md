## Findings

### LOW-1 — ac-09 verification depth less than spec text

The spec verification for ac-09 says: "invokes `<Session as ParamDispatcher>::dispatch(name, value)` and asserts the returned `Vec<(usize, Result<...>)>` equals what `propagate_param` returns for the same inputs (`assert_eq!` over an equivalent fixture session), and `current_params()` agrees."

The shipped test (slider.rs:260-275) does NOT do that. It asserts the trait method's signature via a function-pointer assignment (`let _f: fn(...) = <Session as ParamDispatcher>::dispatch;`) and comments that "End-to-end forwarding equivalence is exercised inside the engine crate's rpw3 tests." No live Session is constructed; no `assert_eq!` against `propagate_param` output runs.

**Mitigation already present:**
- Trait body at slider.rs:50-58 is a single forwarding statement `self.propagate_param(name, value)` — readable in three lines.
- The function-pointer signature pin guarantees the trait method signature matches `propagate_param`'s shape — a divergent return type or arg list would not compile.
- `propagate_param`'s behaviour is exhaustively covered by engine-crate `rpw3_ac04..ac08` and `rpw2_ac02/ac03/ac04`.
- Constructing a fixture Session in the brightfield-ui crate would require importing the engine's test helpers (`parse_and_analyse`) and pulling in DuckDB at test time — heavyweight for what is, materially, a one-line forwarding contract.

**Why LOW (not MEDIUM/HIGH):** the contract is structurally guaranteed by the type system + diff readability + engine-side coverage. The literal assertion in the spec verification is missing, but the ac-09 *description* — "ParamDispatcher::dispatch on Session forwards to propagate_param identically — same return shape, same param_state effect" — is satisfied in substance. This is advisory; it would be tightened in a future revision but does not block ship.

### LOW-2 — Slider GPUI widget (Track + thumb) not shipped

The spec's goal says "ship the first end-to-end input widget (slider)" and a top-level constraint says "Widget surface: ship Slider end-to-end." The ontology_schema describes `Slider` as "GPUI widget — Track + thumb, mouse handlers, current value as overlay state during drag, commits via commit_slider_release on mouse_up."

What landed in `crates/brightfield-ui/src/slider.rs`:
- `ParamDispatcher` trait + `impl` for `Session` (forwarding).
- `SliderBinding` struct + `from_input` constructor (UI-layer binding from an `Input` AST node).
- `SliderState` enum with `Idle/Dragging/Released` transitions.
- `commit_slider_release` pure helper.

What did NOT land:
- No `gpui::Element` / `Render` implementation for a Slider widget.
- No Track + thumb GPUI primitives.
- No mouse_down / mouse_up GPUI event handlers.
- No `ChartView` wiring (intentionally — `implementation_notes` says it's deferred: "a future helper `ChartView::propagate_param_and_redraw` is allowed but not required by this spec").

**Why LOW (not MEDIUM):** ac-12's verification text explicitly says "End-to-end GPUI event simulation is out of scope; the lifted-helper coverage matches the cfs2_ac11 precedent." The ACs were authored to verify the binding + state-machine + dispatch surfaces, not the rendered widget. So strictly per the AC list this passes. But an analyst dragging a slider in the actual app cannot do so today — the slider is purely a state machine on the test bench. Worth flagging as a gap between the goal narrative and the AC scope, even if the spec self-permits it.
