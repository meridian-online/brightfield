## Findings

### [MEDIUM] Prepared statement cache does not skip re-prepare on cache hit
**Category:** bug
**Description:** AC-07 requires: "On scalar param change, the cached prepared statement is reused (rebind only -- no re-prepare)." Implementation note 3 says the cache should be `HashMap<u64, PreparedStatement>`. The actual `CachedStatement` stores `sql: String` and `bindings: Vec<Binding>`, not a DuckDB `PreparedStatement`. On cache hit (line 209), the cached SQL string is read, but `self.conn.prepare(&sql)` is called unconditionally at line 225. The `prepare()` call is never skipped. This means every execution pays the prepare cost regardless of cache state. The v1 CRITICAL finding noted the cache was write-only; the fix made it read SQL strings from the cache, but did not achieve the spec's goal of avoiding re-preparation.

This is downgraded from CRITICAL to MEDIUM because: (a) the cache now has functional read behaviour (SQL string lookup works), (b) DuckDB may internally cache prepared statements making the perf impact negligible, and (c) the `CachedStatement` struct stores binding metadata that could enable future rebind logic. However, the contract from the spec ("rebind only -- no re-prepare") is not met.
**Evidence:** `crates/brightfield-engine/src/lib.rs` lines 201-237. The `CachedStatement` struct at line 121 stores `sql: String`, not `duckdb::Statement`. Line 225 calls `self.conn.prepare(&sql)` on every code path. The `#[allow(dead_code)]` annotation on `CachedStatement` (line 120) further confirms `bindings` is never read.
**Recommendation:** Either (a) store `duckdb::Statement` in the cache and look it up before calling `prepare()`, or (b) if DuckDB's `Statement` lifetime makes this impractical (borrow checker issues with `&Connection`), document that the current implementation is a SQL-string cache that relies on DuckDB's internal prepare cache, and adjust ac-07's description to match. Option (b) is acceptable for this iteration if lifetime constraints are the blocker.

### [MEDIUM] dex_ac06 test is vacuous -- does not exercise filtering
**Category:** test-gap
**Description:** The `dex_ac06_update_param_filters_to_marks` test uses a spec where `threshold` is a declared param but no mark references it (no `filterBy`, no `$threshold` in expressions). The subscriber graph for `threshold` is therefore empty. The assertion `results.is_empty() || results.iter().all(|(_, r)| r.is_err())` passes trivially because `results` is empty -- not because non-mark components were filtered out. The test does not exercise the filtering logic at all. AC-06's verification requires: "a spec with a param-dependent mark and a non-subscribing mark. Call update_param, verify only the subscribing mark appears in the result vec."
**Evidence:** `crates/brightfield-engine/src/lib.rs` lines 518-547. The spec has `params: threshold: 50` but the dot mark's encoding (`x: x, y: y`) does not reference `$threshold`. The subscriber graph for `threshold` will be empty, so `mark_indices` is empty, and the loop at line 178 never executes.
**Recommendation:** Create a spec where the param is actually referenced in a mark's `filterBy` clause (e.g., `filterBy: { "$threshold": { gte: y } }`), so the subscriber graph yields a mark path. Then assert that the result vec contains exactly one entry for that mark (and that the mark index matches). A second non-subscribing mark should be present to prove filtering works.

### [LOW] ac-05 test does not demonstrate partial failure (mixed Ok + Err)
**Category:** test-gap
**Description:** AC-05's verification specifies "Integration test with a spec containing both a supported (test-only) and unsupported mark: one Ok, one Err." The `dex_ac05_execute_all_partial_failure` test uses dot + line marks, both unsupported, so both fail. This proves `execute_all` returns per-mark results but does not demonstrate partial failure (mixed Ok + Err). The `test_execute_emitted` helper added for ac-07 could be adapted to create a test-only success path, but ac-05 itself was not updated.
**Evidence:** `crates/brightfield-engine/src/lib.rs` lines 429-449. Both results are asserted as `Err`.
**Recommendation:** Use the `test_execute_emitted` pattern (hand-crafted `EmittedQuery`) to make one mark succeed while another mark goes through `execute_mark` and hits `UnsupportedMark`. This may require exposing the ability to inject a pre-computed result for a specific mark index, or refactoring `execute_all` to accept an override map.

### [LOW] ac-03 missing CSV-with-unknown-extras warning test
**Category:** test-gap
**Description:** AC-03's verification specifies: "Test with a CSV source containing unknown extras -- load_spec succeeds and warnings are accessible via ddl_warnings()." The existing `dex_ac03` test only checks inline data queryability. The `ddl_warnings()` accessor exists but is never tested.

### [LOW] ac-08 missing QueryFailed test

## Honest Assessment

The fix commit (`cc73cc7`) addressed the most visible issues from the v1 review: the unused import is gone, dex_ac06 and dex_ac07 tests exist, and the cache now reads on hit. The structural separation is clean, error modelling is solid, and the full API shape (Engine/Session/LoadResult, execute_mark, execute_all, update_param) matches the spec. All 198 tests pass with zero warnings.

However, two substantive issues remain. First, the prepared statement cache stores SQL strings rather than DuckDB `PreparedStatement` objects, so `conn.prepare()` is called on every execution -- the spec's "rebind only, no re-prepare" contract is not met. This may be a pragmatic concession to Rust lifetime constraints (storing `Statement<'_>` in a `HashMap` alongside the `Connection` it borrows from is non-trivial), but should be explicitly acknowledged. Second, the ac-06 test is vacuous -- it passes because the subscriber graph is empty, not because non-mark components were filtered. This means the core reactive update path has no real test coverage.

The remaining LOW findings (ac-03 warnings, ac-05 mixed partial failure, ac-08 QueryFailed, ac-04 success path) are genuine gaps but individually minor. Collectively they represent about 40% of the AC verification steps being partially or weakly covered. The two MEDIUM findings (cache re-prepare, vacuous ac-06 test) are the blocking items for this review cycle.
