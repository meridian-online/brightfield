## Findings

### [LOW] Clippy: render_interpolated has too many arguments (8/7)
**Category:** performance
**Description:** `MarkRenderer::render_interpolated()` takes 8 parameters (including `&self`), exceeding clippy's default threshold of 7. This is a consequence of the spec's requirement to forward `highlight` alongside the interpolation parameters.
**Evidence:** `crates/brightfield-render/src/mark.rs:50` -- `fn render_interpolated(&self, scene, batch, channel_map, scales, _prev_positions, _t, highlight)`.
**Recommendation:** Suppress with `#[allow(clippy::too_many_arguments)]` on the trait method, or bundle `(prev_positions, t)` into a small `InterpolationParams` struct. The latter is cleaner but out of scope for this card -- the current shape matches the spec exactly.

### [LOW] Clippy: collapsible if in find_nearest
**Category:** bug
**Description:** Two nested `if` statements in `find_nearest` can be collapsed into a single `if dist <= max_dist && best.as_ref().map_or(true, |b| dist < b.distance)`. Clippy warns but this is purely stylistic.
**Evidence:** `crates/brightfield-render/src/nearest.rs:86-94`.
**Recommendation:** Collapse the two conditions into one. One-line fix.

### [LOW] LineRenderer ignores highlight parameter
**Category:** test-gap
**Description:** `LineRenderer::render()` accepts `_highlight: Option<&HighlightState>` (prefixed with underscore, unused). The spec constraint says "all three renderers (Dot, Bar, Line) respect it", but `LineRenderer` discards it. This is defensible -- per-segment highlight for a line is semantically ambiguous (dim which segments?) -- but there is no `ifb_ac04_line_renderer_with_highlight` test to document this conscious decision.
**Evidence:** `crates/brightfield-render/src/mark.rs:389` -- `_highlight: Option<&HighlightState>`. The ac-04 tests cover Dot and Bar only.
**Recommendation:** Add a brief comment on the `_highlight` parameter explaining why line highlight is deferred (segment ambiguity). Optionally add a test that passes `Some(&hs)` and asserts the scene still renders (documenting that highlight is accepted but not applied). Not a blocker.

## Honest Assessment

This is a clean, well-structured implementation that delivers all 10 acceptance criteria with thorough test coverage. The new modules (nearest.rs, tooltip.rs, transition.rs) are focused and well-documented. The `HighlightState` predicate correctly uses `Send + Sync` bounds as specified. The `render_interpolated` default-impl-forwards-highlight constraint is met. Existing tests all pass -- backward compatibility is preserved through the additive `Option<&HighlightState>` parameter and the new `highlight: None` field on `ChartData`. The two new clippy warnings are minor (too-many-args on the trait method is arguably a spec-driven design choice, and the collapsible-if is cosmetic). The only substantive observation is that `LineRenderer` silently ignores highlight, which is reasonable but worth a comment. Overall, this is ready to merge.
