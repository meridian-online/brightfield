## Findings

### [CRITICAL] Prepared statement cache is populated but never actually reused
**Category:** bug
**Description:** The `execute_emitted` method populates the `cache` HashMap (line 203-208) with a `CachedStatement` but then always calls `self.conn.prepare(&emitted.sql)` fresh (line 212). The cached entry is never read back — it is write-only. This means:
1. The cache has no functional effect on execution — scalar param changes re-prepare every time.
2. AC-07 requires "the cached prepared statement is reused (rebind only — no re-prepare)" — this is not implemented.
3. The spec's implementation note 3 says "The prepared statement cache is a HashMap<u64, PreparedStatement>" but the actual `CachedStatement` stores `sql: String` and `bindings: Vec<Binding>`, not a DuckDB `PreparedStatement`.
**Evidence:** `crates/brightfield-engine/src/lib.rs` lines 196-225. The cache is inserted into at line 203 and read only by `cache_len()` at line 240 (test-only). No code path reads from the cache to skip `conn.prepare()`.
**Recommendation:** Either store `duckdb::Statement` in the cache and look it up before preparing, or if DuckDB's `Statement` lifetime makes caching difficult, document this as a known limitation and adjust ac-07 verification accordingly. The current code gives the illusion of caching without the behaviour.

### [MEDIUM] No tests for ac-06 (update_param)
**Category:** test-gap
**Description:** AC-06 requires tests for `update_param` — specifically: (a) only subscribing marks appear in the result, (b) partial failure with one success and one failure. No `dex_ac06` test exists. The `update_param` method exists and looks structurally correct, but is entirely untested.
**Evidence:** `grep -n 'dex_ac06' crates/brightfield-engine/src/lib.rs` returns no results. The progress.md claims ac-06 is checked off.
**Recommendation:** Add at least two tests: one verifying filtering (non-subscribing marks excluded) and one verifying partial failure semantics.

### [MEDIUM] No tests for ac-07 (prepared statement cache)
**Category:** test-gap
**Description:** AC-07 requires tests verifying cache behaviour — specifically that `cache_len()` stays constant across scalar rebinds and that selection updates produce different plan_hash values. No `dex_ac07` test exists. Combined with the CRITICAL finding that the cache is non-functional, this means the entire caching story is unverified.
**Evidence:** `grep -n 'dex_ac07' crates/brightfield-engine/src/lib.rs` returns no results.
**Recommendation:** Write the tests specified in ac-07 verification. These tests will likely expose the cache non-functionality from the CRITICAL finding.

### [MEDIUM] ac-05 test does not demonstrate partial failure
**Category:** test-gap
**Description:** AC-05 specifies "Integration test with a spec containing both a supported (test-only) and unsupported mark: one Ok, one Err." The actual test `dex_ac05_execute_all_partial_failure` uses two unsupported marks (dot and line), both of which fail. This tests that `execute_all` returns per-mark results, but does not demonstrate the partial failure case (mixed Ok + Err) that the AC requires.
**Evidence:** `crates/brightfield-engine/src/lib.rs` lines 393-413. Both marks are unsupported; the test asserts both are `Err`.
**Recommendation:** Create a test-only lowerer (as the spec's implementation note 4 suggests) that makes one mark succeed while the other fails. This would also provide the success-path test missing from ac-04.

### [LOW] ac-03 missing CSV-with-unknown-extras warning test
**Category:** test-gap
**Description:** AC-03's verification specifies: "Test with a CSV source containing unknown extras -- load_spec succeeds and warnings are accessible via ddl_warnings()." The `dex_ac03` test only checks inline data queryability, not the warning path.
**Evidence:** Only one `dex_ac03` test exists. It does not exercise `ddl_warnings()`.
**Recommendation:** Add a test loading a CSV spec with an unknown extra key, then assert `session.ddl_warnings()` is non-empty.

### [LOW] ac-08 missing QueryFailed test
**Category:** test-gap
**Description:** AC-08's verification requires both a DdlFailed test AND a QueryFailed test ("A test-only lowerer emitting invalid SQL produces QueryFailed with the mark index"). Only the DdlFailed path is tested.
**Evidence:** `dex_ac08_ddl_failed_nonexistent_parquet` is the only ac-08 test.
**Recommendation:** Add a test that produces a QueryFailed error with mark_index verification.

### [LOW] Unused import warning
**Category:** bug
**Description:** `use brightfield_sql::error::EmitError` at lib.rs:26 is only used in `#[cfg(test)]` blocks, producing a compiler warning.
**Evidence:** `cargo test --workspace 2>&1 | grep warning` shows: "unused import: `brightfield_sql::error::EmitError`"
**Recommendation:** Move the import inside the `#[cfg(test)] mod tests` block, or gate it with `#[cfg(test)]`.

### [LOW] execute_all assumes contiguous 0..N mark indices
**Category:** edge-case
**Description:** `execute_all` iterates `0..mark_count` where `mark_count = self.mark_index_map.len()`. The `build_mark_index_map` function assigns indices via `.enumerate()` on the collected marks vector, so they will be 0..N contiguous. This works today, but `execute_mark(index)` passes the index directly to `emit_query` — if the mark_index_map ever produces non-contiguous indices, `execute_all` would iterate wrong indices. This is not a bug currently but is fragile.
**Evidence:** `crates/brightfield-engine/src/lib.rs` lines 144-147 and 245-255.
**Recommendation:** No immediate action needed. The current implementation is correct for how indices are assigned.

## Honest Assessment

The structural separation is clean — the engine crate correctly sits downstream of spec and sql with no reverse dependencies. The error modelling is well-done with structured context in every variant. The `load_spec` / `execute_mark` / `execute_all` / `update_param` API shape matches the spec. However, the implementation has a significant gap: the prepared statement cache is write-only and never reused, which is the core of ac-07 and a key design goal of the spec. Additionally, 3 of 10 testable ACs have no tests at all (ac-06, ac-07, ac-08 QueryFailed path), and ac-05's test does not actually demonstrate partial failure. The progress.md reports all ACs as complete, which overstates the current state. The CRITICAL cache finding and the missing ac-06/ac-07 tests should be addressed before merge.
