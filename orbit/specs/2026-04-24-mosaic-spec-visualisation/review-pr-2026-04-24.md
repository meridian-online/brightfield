## Findings

### [CRITICAL] AC-04: GPUI window code is commented out

**Category:** test-gap
**Description:** The spec's AC-04 requires the app to "open a window with ChartView." The GPUI window code in `main.rs:162-176` is entirely commented out with a note that it is "deferred to a future build with full Xcode + Metal." The binary runs headlessly — it executes the pipeline and prints scene stats, but never opens a window.

The progress.md documents this as a detour ("GPUI window deferred: full Xcode + Metal compiler needed for gpui_macos"), which is a legitimate platform constraint. However, the spec verification says "A smoke test with a valid spec YAML file opens a window (manual verification)" — this cannot be satisfied in the current state.

**Evidence:** `crates/brightfield-app/src/main.rs:162-176` — all GPUI window code is commented out.
**Recommendation:** Either (a) add the `gpui_macos` platform dependency and uncomment the window code behind a feature flag that can be tested on macOS, or (b) amend the spec to acknowledge the headless pipeline as the v1 deliverable and add a follow-up card for GPUI window integration. Option (b) seems more pragmatic given the platform dependency constraint.

### [MODERATE] AC-05: No test for graceful mark failure in the app pipeline

**Category:** test-gap
**Description:** AC-05 requires a unit test in the app crate: "a spec with one valid mark and one invalid mark produces a scene from the valid mark only." No `msv_ac05` test exists. The graceful failure logic is present in `run_pipeline()` (lines 72-79 of main.rs: `Err(e) => { eprintln!("warning: skipping mark {i}: {e}"); }`), and the engine's `dex_ac05_execute_all_partial_failure` test covers the engine layer. But the spec explicitly requires an app-level test.

**Evidence:** `grep -r msv_ac05 crates/` returns no results.
**Recommendation:** Add a test in the app crate (or as an integration test) that exercises `run_pipeline()` with a spec containing one valid dot mark and one unsupported mark (e.g., `rect`), asserting the scene is non-empty and only the valid mark contributes.

### [LOW] Spec says MarkKind::Bar but the enum has no Bar variant

**Category:** spec-inaccuracy
**Description:** The spec's AC-01 says SimpleLowerer should be "registered in default_lowerers() for MarkKind::Dot, MarkKind::Line, MarkKind::Bar, MarkKind::BarX, MarkKind::BarY" (5 kinds). The `MarkKind` enum has no `Bar` variant — only `BarX` and `BarY`. The implementation correctly registers 4 kinds (Dot, Line, BarX, BarY). The test `msv_ac01_default_lowerers_contains_all_registered_kinds` asserts `kinds.len() == 4`.

**Evidence:** `crates/brightfield-spec/src/vocab.rs` — no `Bar` variant in `MarkKind`. `crates/brightfield-sql/src/lower.rs` — `default_lowerers()` registers 4 kinds.
**Recommendation:** No code change needed. The implementer correctly adapted to the actual API. The spec should be corrected to say "Dot, Line, BarX, BarY" (4 kinds) for accuracy.

### [LOW] `collect_marks` made pub without a public re-export

**Category:** API hygiene
**Description:** `collect_marks` in `brightfield-sql/src/emit.rs` was changed from `fn` to `pub fn` so the app crate can call it directly via `brightfield_sql::emit::collect_marks`. This works because emit is a public module, but the function isn't re-exported from the crate root (`lib.rs`). It is an internal function used by the app crate for mark indexing during the pipeline.

**Evidence:** `crates/brightfield-sql/src/emit.rs:229` — `pub fn collect_marks`.
**Recommendation:** Either re-export from `lib.rs` for a clean public API, or document that the app crate is the only intended consumer. Low priority.

### [INFO] Dependency constraint preserved

**Category:** verification
**Description:** The spec constraint "brightfield-render must NOT gain dependencies on brightfield-engine or brightfield-sql" and "brightfield-ui must NOT gain dependencies on brightfield-engine or brightfield-sql" are satisfied. `brightfield-ui/Cargo.toml` has `brightfield-engine` as a dependency, but this is pre-existing on main (not introduced by this PR). `brightfield-render/Cargo.toml` has no engine or SQL dependencies.

### [INFO] UI crate substantially rewritten

**Category:** scope
**Description:** The diff includes significant rewrites of the UI crate: new files (`chart_layout.rs`, `chart_state.rs`, `chart_view.rs`, `vello_renderer.rs`) and a rewrite of `chart_element.rs` from a stub to a full GPUI Element implementation. The `gpu-tests` feature flag gates tests that require a GPU context.

## Honest Assessment

The implementation delivers a clean, well-tested spec-to-scene pipeline. The SQL lowering layer (SimpleLowerer), multi-mark scale inference, and multi-mark scene building are solid — each with thorough tests that match the spec's verification criteria. The graceful failure logic works correctly at the engine layer. The two gaps are: (1) the GPUI window is commented out due to a platform dependency constraint (gpui_macos requires Xcode + Metal), making AC-04's window-opening requirement unverifiable, and (2) AC-05 lacks an app-level test despite the logic being present. The window gap is a pragmatic call — the headless pipeline proves end-to-end correctness — but it should be explicitly acknowledged in the spec or resolved with a feature-gated build. Adding the AC-05 test is straightforward and should be done before merge.
