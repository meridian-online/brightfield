## Findings

### [LOW] SpecAnalysis not embedded in ParseOutput

**Category:** design
**Description:** AC-09 says "ParseOutput (or a new SpecAnalysis struct) exposes the subscriber graph and topological order alongside the existing Spec and warnings." The implementation chose the "new SpecAnalysis struct" path, which is valid per the spec's wording. However, `analyse_spec()` is a separate call the consumer must invoke after `parse_spec()`. This is a two-step API: parse, then analyse. The spec's intent was for analysis to be "integrated into the parse pipeline" -- the current design meets the letter but requires the consumer to know about and call `analyse_spec()` separately.
**Evidence:** `parse_spec()` in `crates/brightfield-spec/src/parse.rs` returns `ParseOutput { spec, warnings, base_dir }` with no analysis. `analyse_spec()` in `crates/brightfield-spec/src/analysis.rs` takes a `&Spec` and returns `SpecAnalysis`.
**Recommendation:** Acceptable as-is. The two-step design avoids paying the analysis cost for consumers that only need parsing. A convenience `parse_and_analyse()` function could be added later if the pattern becomes common.

### [LOW] Subscriber graph does not collect param refs from ExpressionNode.params

**Category:** test-gap
**Description:** The spec's implementation notes say "one pass over the component tree collecting ParamRef occurrences from expressions (ExpressionNode.params), filter_by fields, and from_source fields." The subscriber graph walker (`collect_mark_subscribers`, `collect_input_subscribers`) walks `options` for direct `ValueOrParamRef::Param` values but does not descend into `SpecValue::Expression` variants to extract their `.params` vectors. If a mark option contains a SQL expression like `"$threshold + 10"`, the `threshold` param would be inside an `ExpressionNode.params` list, not a direct `ValueOrParamRef::Param`. The current `collect_spec_value_subscribers` handles `Object` and `Array` recursion but has an empty `_ =>` arm that skips `Expression` variants.
**Evidence:** `crates/brightfield-spec/src/analysis.rs` lines 231-246 (`collect_spec_value_subscribers`): the match arm for `SpecValue::Expression(_)` falls through to `_ => {}`.
**Recommendation:** Add a match arm for `SpecValue::Expression(expr)` that iterates `expr.params` and adds each to the subscriber graph. This is low severity because (a) the current corpus exercises this path minimally -- most param refs are direct `$param` forms that get lifted to `ValueOrParamRef::Param`, not embedded in SQL expressions, and (b) the spec's AC-03 verification only requires "known param references" which the tests cover with direct refs. However, this is a latent gap that will matter when SQL-expression-embedded params become common.

### [LOW] `collect_spec_value_subscribers` does not handle `SpecValue::Param`

**Category:** edge-case
**Description:** `SpecValue` has a `Param(ParamRef)` variant (visible in `ParamDeclaredType::from_param_node` which matches it). The `collect_spec_value_subscribers` function's `_ => {}` arm silently drops this case. A `SpecValue::Param` nested inside an `Object` or `Array` would not register as a subscriber.
**Evidence:** `crates/brightfield-spec/src/analysis.rs` lines 231-246.
**Recommendation:** Add `SpecValue::Param(pr) => { graph.entry(pr.0.clone()).or_default().push(ComponentPath(path.to_string())); }` to the match. Low severity for the same reason as above -- the parser lifts `$param` at the `ValueOrParamRef` level before it can appear as a nested `SpecValue::Param`.

### [INFO] sqlparser added as dependency in Cargo.lock

**Category:** dependency
**Description:** The diff adds `sqlparser` (0.61.0) plus its transitive deps (`recursive`, `stacker`, `psm`, `cc`, etc.) to `Cargo.lock` for both `brightfield-conformance` and `brightfield-sql`. This is unrelated to the reactive-parameters feature -- it appears to be from a concurrent change on the base branch or a prior commit. The dependency is reasonable for a SQL-processing project and does not affect this feature.
**Evidence:** `Cargo.lock` diff lines adding `sqlparser`, `recursive`, `stacker`, etc.
**Recommendation:** No action needed. Noting for awareness.

## Edge Case Probing

**First run (no prior state):** The analysis functions are pure -- they take a `&Spec` and return results. No filesystem, no database. No first-run concerns.

**Failure modes:** `build_dependency_dag` correctly returns `Err(SchemaViolation)` on cycles. `analyse_spec` propagates this. Non-fatal conditions (dead params, type mismatches) produce warnings, not errors. Correct.

**Idempotency:** All functions are pure and deterministic for a given `Spec`. Multiple calls produce identical results.

**Boundary conditions:** Empty specs (no params, no inputs) produce empty analysis with no warnings -- tested by `rpw_ac10`. Single-param specs with no references produce `DeadParam` -- tested by `rpw_ac04`. Self-referential cycle (param writes to itself) is not explicitly tested but would be caught by Kahn's algorithm as a cycle.

## Honest Assessment

This is a clean, well-structured implementation. The new `analysis.rs` module is 838 lines of pure, well-documented Rust with 16 tests covering all acceptance criteria. The typed fields on `Input` (ac-01) are correctly extracted during parsing and re-emitted during serialisation, preserving round-trip fidelity. The subscriber graph, DAG, and type-mismatch analysis are cleanly separated functions composed by `analyse_spec()`. The two substantive findings -- missing `ExpressionNode.params` traversal and missing `SpecValue::Param` handling in the subscriber graph walker -- are latent gaps that do not affect current corpus behaviour but will need attention when SQL-expression-embedded param refs become common. Neither is a blocker. All 168 tests pass, vendored specs round-trip correctly, and the implementation respects every constraint in the spec.
