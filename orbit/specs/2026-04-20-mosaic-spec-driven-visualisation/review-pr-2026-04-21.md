## Findings

### [HIGH] F1 — ac-05 test does not parametrise over LIFT_SURFACE_FIELDS

**Category:** test-gap
**Description:** The spec's ac-05 verification requires: *"Unit test `parse::lifts_param_string_and_object_forms` parametrises over every entry in `LIFT_SURFACE_FIELDS`, parses both forms at that position, and asserts AST equality to `ParamRef(\"foo\")`. Test compiles to one assertion per field, so omissions surface as fails, not as silent under-coverage."*

The implementation's ac-05 test suite is `dfspec_ac05_dollar_ident_detection` and `dfspec_ac05_maybe_lift_string_and_object_shorthands`. Both test the *helpers* (`dollar_ident`, `maybe_lift`) in isolation. Neither iterates `LIFT_SURFACE_FIELDS`; the spec's "omissions surface as fails, not as silent under-coverage" guarantee is absent. Today, if a field is dropped from the `LIFT_SURFACE_FIELDS` constant or wired incorrectly in `Walker::lift_field`, no test would fail.

**Evidence:**
- `crates/brightfield-spec/src/parse.rs:1383-1409` — the two ac-05 tests; `grep dfspec_ac05` returns nothing that mentions `LIFT_SURFACE_FIELDS`.
- `crates/brightfield-spec/src/parse.rs:38-158` — the constant has ~95 fields; none are asserted individually.

**Recommendation:** Add a parametrised test that, for each entry in `LIFT_SURFACE_FIELDS`, constructs a minimal YAML snippet placing the field inside a mark/legend/input parent, parses, and asserts the options map contains `ValueOrParamRef::Param(ParamRef("foo"))` for both string form `"$foo"` and object form `{param: "foo"}`.

### [MEDIUM] F2 — Config and PlotDefaults are type aliases, not structs

**Category:** bug
**Description:** Spec ac-02 enumerates the struct list as *"(a) **Structs** — `Spec`, `Meta`, `Config`, `PlotDefaults`, …"*. The implementation defines both as `type Config = IndexMap<String, SpecValue>` / `type PlotDefaults = IndexMap<String, SpecValue>`. This is a deliberate choice explained by Detour D1 (narrowing `deny_unknown_fields` after corpus evidence). It passes corpus totality, but the spec's constraint list was not re-written to match. The progress.md references D1 but the spec.yaml still lists them as structs under ac-02.

**Evidence:**
- `crates/brightfield-spec/src/ast.rs:61-65`:
  ```rust
  pub type Config = IndexMap<String, SpecValue>;
  pub type PlotDefaults = IndexMap<String, SpecValue>;
  ```
- Spec ac-02 description explicitly lists `Config`, `PlotDefaults` as Structs.

**Recommendation:** Either (a) re-introduce `Config` / `PlotDefaults` as newtype-struct wrappers around the `IndexMap` to honour the literal contract (`pub struct Config(pub IndexMap<String, SpecValue>);`), or (b) update the spec.yaml ac-02 description to match the D1-narrowed outcome and keep the type aliases. Option (b) is consistent with the recorded detour intent — AC-02 should describe the delivered shape.

### [MEDIUM] F3 — ac-07 has no dedicated tests

**Category:** test-gap
**Description:** The spec's ac-07 verification requires two tests: `parse::rejects_unknown_in_meta` and `parse::warns_on_unknown_option`. After Detour D2, the "rejects" assertion was to flip to a "warns" assertion ("the meta-strictness assertion becomes a warning-emission assertion, not a fatal-error assertion"). Neither test exists. A grep for `dfspec_ac07` returns zero hits. The behaviour IS implemented (`walk_meta` at `parse.rs:367-370`, `walk_open_map` at `parse.rs:388-428`) but nothing locks it in.

**Evidence:**
- Grep of the crate for `dfspec_ac07` / `unknown_in_meta` / `unknown_option` returns no test functions.
- `crates/brightfield-spec/src/parse.rs:360-372` — the walk_meta unknown-key path emits `ParseWarning::UnknownOption` with no test coverage.

**Recommendation:** Add `dfspec_ac07_meta_unknown_key_warns` asserting a spec with `meta: { bogus: true }` parses successfully and emits exactly one `ParseWarning::UnknownOption { path: "meta", key: "bogus" }`. Add `dfspec_ac07_mark_unknown_option_is_accepted` asserting `mark: dot` with an unknown option key parses (unknown keys on option bags go into the AST without warning per the current implementation).

### [MEDIUM] F4 — ac-11 corpus round-trip is not a corpus test

**Category:** test-gap
**Description:** ac-11 verification calls for *"Integration test `tests/roundtrip.rs::every_corpus_spec_round_trips` iterates the vendored corpus and asserts `parse_spec(serialise(parse_spec(s))).spec == parse_spec(s).spec` per spec."* The delivered ac-11 coverage is a single unit test (`dfspec_ac11_ast_round_trip_idempotent`) against one inline YAML snippet that exercises meta + params.crossfilter + mark.dot with one filterBy. The vendored corpus has 54 files exercising much richer vocabulary (all mark kinds, concat layouts, interactor/input options, SQL expressions, inline data arrays, legend components). None of those are round-tripped.

**Evidence:**
- `ls crates/brightfield-spec/tests/` → `corpus_totality.rs crossfilter.rs diagnostics.rs` — no `roundtrip.rs`.
- `crates/brightfield-spec/src/parse.rs:1507-1525` — `dfspec_ac11_ast_round_trip_idempotent` covers one inline spec only.

**Recommendation:** Add `crates/brightfield-spec/tests/roundtrip.rs` iterating the same 54-file corpus used by `corpus_totality`, parsing → serialising → reparsing each and asserting AST equality. The `Spec`, `Component`, `SpecValue`, etc. already derive `PartialEq`, so this is mostly boilerplate matching `corpus_totality.rs`.

## Honest Assessment

The core parser is solid work. Option Z discipline is clean: no `Other` variants, sealed registry enums, `ImplStatus` on every variant, `ParamRef` canonicalising to `$name` on serialisation, and zero `miette` coupling. The full 54-file Mosaic corpus parses with only warnings, the crossfilter structural invariants hold, and the error enum carries spans where the deserialiser provides them. The D1/D2 detours are well-reasoned responses to corpus evidence and demonstrate the narrowing is empirically driven, not speculative.

The gaps are in test *coverage fidelity*, not behavioural correctness. The implementation does the right thing in all five flagged areas, but the spec-declared tests that would *lock* that behaviour against regression were either downgraded (ac-05, lift surface not parametrised; ac-11, only one inline spec) or elided (ac-07 has no named tests; ac-14 case (c) is orphaned after D2). Two of those gaps are one-shot test adds; F2 is a choice between relaxing the spec or restoring struct types; F5 is a bookkeeping fix in spec.yaml. None are behavioural defects in the parser itself — the review gate is about whether the spec's exit conditions are met, and by the spec's own rubric two of five aren't. Hence REQUEST_CHANGES rather than APPROVE.

Recommended minimum set to flip to APPROVE: F1 (parametrised lift-surface test), F4 (corpus roundtrip.rs), and one of F2's two options (re-wrap Config/PlotDefaults as newtypes, or amend spec.yaml to ratify the D1 outcome). F3 and F5 are lower priority but cheap to knock over at the same time.
