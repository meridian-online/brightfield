## Findings

### [CRITICAL] ac-11 missing test — no `nav_ac11` test in any crate
**Category:** test-gap
**Description:** AC-11 requires that the six InteractorKind Pan/PanZoom variants are flipped from `Unimplemented` to `Implemented` in `vocab.rs`. The implementation is correct (confirmed by grep: all six variants show `Implemented` at lines 208-213 of `crates/brightfield-spec/src/vocab.rs`), but there is no `nav_ac11` prefixed test anywhere in the codebase. The spec's `ac_type` is `code` and its verification says "Grep vocab.rs for the six variants and assert Implemented status."
**Evidence:** `grep -r 'nav_ac11' crates/` returns no results. The spec requires a test for every `code`-typed AC.
**Recommendation:** Add a test in `brightfield-spec` (e.g., `crates/brightfield-spec/src/vocab.rs` tests module) that asserts all six variants return `Implemented` status. Example pattern: call each variant's status method and assert it equals `ImplementationStatus::Implemented`.

### [LOW] `Session::update_extent` always registers a pass even when both extents are None
**Category:** performance
**Description:** The spec's implementation note 8 says "The pass is only registered when ViewExtent has at least one Some axis — no pass registration at full extent." The current implementation always creates a `NavigationFilterPass` and puts it in the `passes` vec, even when both `x_extent` and `y_extent` are `None`. The pass's `apply` method is a no-op when it has no filters, so this is functionally correct, but it violates the stated design intent.
**Evidence:** `crates/brightfield-engine/src/lib.rs` lines 218-220 (in the diff): `NavigationFilterPass::from_extents(x_extent, y_extent)` is called unconditionally and always pushed into the passes vec. The pass then runs as a no-op identity transform.
**Recommendation:** Add a short-circuit: if both extents are `None`, skip pass registration entirely and delegate to the existing `execute_all` path. This is a minor optimisation that also makes the code match the stated intent.

### [LOW] Debounce test `nav_ac08_debounce_settles_after_duration` uses `thread::sleep`
**Category:** test-gap
**Description:** The spec review (review-spec-2026-04-22.md) flagged this as a potential flakiness risk. The implementation uses `Duration::from_millis(1)` debounce with a `sleep(5ms)`, which provides a 5x margin. This is pragmatic and unlikely to be flaky in practice, but the spec review's recommendation to use a mockable clock was not adopted. Noting for completeness — not blocking.
**Evidence:** `crates/brightfield-ui/src/interaction.rs` test `nav_ac08_debounce_settles_after_duration` at line ~1258 in the diff.
**Recommendation:** Accept as-is. The 5x margin is sufficient for CI. A clock abstraction can be introduced if flakiness materialises.

### [LOW] `emit_query_with_passes` ignores `_param_values` parameter
**Category:** bug (latent, non-blocking)
**Description:** The `_param_values` parameter in `emit_query_with_passes` is prefixed with `_` and unused. This matches the existing `emit_query` function which also ignores it (it is a placeholder for D4 hybrid binding mode, not yet implemented). Consistent with the codebase, but worth noting that navigation filter re-queries will not honour runtime param values when they are eventually wired.
**Evidence:** `crates/brightfield-sql/src/emit.rs` line 320: `_param_values: Option<&ParamValues>`. Same pattern at line 272 in the original `emit_query`.
**Recommendation:** No action now. When D4 hybrid binding lands, both functions will need updating together.

## Honest Assessment

This is a well-structured implementation that correctly delivers 10 of 11 acceptance criteria with thorough tests. The architecture cleanly separates concerns: ViewExtent in brightfield-render, NavigationConfig and NavigationState in brightfield-ui, NavigationFilterPass in brightfield-sql, and Session::update_extent in brightfield-engine. The code respects all spec constraints (immutable Scale, no new IR nodes, Band/Colour no-ops). The single blocking issue is the missing `nav_ac11` test — the implementation itself is correct (the vocab.rs changes are verified by grep), but the spec requires a test for every `code`-typed AC. Adding the test is straightforward (a few lines asserting `Implemented` status on the six variants). Once that is addressed, this is ready to merge.
