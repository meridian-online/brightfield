## Findings

### [LOW] RGBA-to-BGRA conversion in paint() may be unnecessary
**Category:** performance
**Description:** `paint()` in `chart_element.rs` performs a manual RGBA-to-BGRA swap on every pixel (`pixel.swap(0, 2)` in a loop). However, the pixel buffer is then wrapped in `image::RgbaImage` (which assumes RGBA layout) and passed to `RenderImage::new()`. If GPUI's `RenderImage` actually expects RGBA (matching the `RgbaImage` wrapper), this swap would produce incorrect colours. If GPUI expects BGRA, then the swap is correct but the `RgbaImage` wrapper name is misleading.
**Evidence:** `crates/brightfield-ui/src/chart_element.rs` lines 128-137. The comment says "RenderImage expects BGRA format" but this should be verified against GPUI's actual expectations.
**Recommendation:** Verify empirically with a visible chart that colours are correct. If GPUI does expect BGRA, consider adding a brief comment citing the GPUI source. If colours are wrong (red/blue swapped), remove the swap. This is a runtime-visible issue that will be caught on first smoke test.

### [LOW] Per-frame texture and buffer allocation in render_to_pixels()
**Category:** performance
**Description:** Every call to `render_to_pixels()` creates a new wgpu texture, render target view, readback buffer, and command encoder. For a static chart this is acceptable, but during interactive brushing or resize (which trigger repaints), this allocates and deallocates GPU resources every frame. On Apple Silicon unified memory the cost is low, but it could become a bottleneck for complex scenes.
**Evidence:** `crates/brightfield-ui/src/vello_renderer.rs` lines 122-170. Each call creates texture + buffer + encoder.
**Recommendation:** No change needed for v2. If profiling reveals paint() exceeding 10ms (per the exit condition), the first optimisation would be to cache the texture and readback buffer at fixed dimensions and only recreate on resize.

### [LOW] Mutex lock held across GPU submission and readback in paint()
**Category:** performance
**Description:** The `renderer.lock()` in `paint()` holds the Mutex for the entire duration of `render_to_pixels()`, which includes GPU command submission and synchronous readback (`device.poll(Maintain::Wait)`). Since GPUI paint is single-threaded, this causes no contention in practice, but it means the lock is held for the full GPU round-trip latency.
**Evidence:** `crates/brightfield-ui/src/chart_element.rs` line 133: `self.renderer.lock().expect(...)`. The lock is held through the entire render_to_pixels call including the blocking poll.
**Recommendation:** No change needed. The spec explicitly states "Vello rendering is synchronous in paint() -- no background threading for v2." The Mutex is structurally correct (VelloInner is not Sync). If async rendering is added later, the lock scope would need to narrow.

### [INFO] ChartView mouse handlers are public methods, not wired to GPUI events
**Category:** test-gap
**Description:** The mouse event handlers (`on_mouse_down`, `on_mouse_move`, `on_mouse_up`, `on_scroll`) are implemented as public methods on ChartView but are not wired to GPUI's event system (e.g., via `on_mouse_down_out` or `InteractiveElement` handlers). They are tested at the coordinate-transform and state-transition level, which satisfies the spec's verification criteria. The actual GPUI event wiring will happen when the app shell is built.
**Evidence:** `crates/brightfield-ui/src/chart_view.rs` lines 60-121. Methods accept explicit `window_pos` and `element_origin` parameters rather than GPUI event structs. The spec's implementation notes acknowledge this: "NavigationState and Transition... event-routing integration is deferred to the app shell card."
**Recommendation:** No change needed. The handlers establish the correct API surface and coordinate transform logic. GPUI event wiring is correctly deferred.

## Honest Assessment

This is a clean, well-structured implementation that faithfully delivers the spec's nine acceptance criteria. The architecture is sound: ChartState owns all mutable state, ChartElement is a stateless rendering shell, VelloRenderer is properly shared via Arc<Mutex>, and the dependency boundary (no gpui in brightfield-render) is respected. The test coverage is thorough for what can be tested without a GPUI runtime -- 9 GPU-gated tests cover VelloRenderer and ChartState, 16 non-GPU tests cover coordinate mapping and interaction state transitions, and all 337 pre-existing tests pass unchanged. The implementation matches the progress.md self-report accurately. The only finding worth verifying empirically is the RGBA-to-BGRA colour swap in paint(), which will be immediately visible on first smoke test. The detour to use `vello::wgpu` re-exports instead of standalone wgpu (to avoid version conflicts) was a pragmatic choice that also cleaned up the Cargo.lock by removing duplicate wgpu/naga/metal crate versions.
